{% comment %} Renders the weekly time-blocking grid as a real HTML (PRD §9.2 "Grid": native `rowspan` support beats fighting CSS Grid for vertical block merges). Self-sufficient: its only input is `week_grid` (an `apps.planner.grid.WeekGrid`), so it renders identically wherever it's included -- the standalone page (`planner/grid.html`, PRD 5.2.2) and the dashboard (`core/dashboard.html`, PRD 5.2.1) both `{% include %}` this one partial rather than duplicating the table markup (PRD §9, R5). Usage: {% include 'planner/partials/grid_table.html' with week_grid=week_grid %} Template contract (from apps/planner/grid.py -- load-bearing for valid HTML): a `'block-start'` cell renders exactly one `
` (via block_cell.html); an `'occupied'` cell renders nothing at all, not even an empty `` -- the `rowspan` above already accounts for its row/column position, and an extra `` here would desync every column to its right; an `'empty'` cell renders a normal clickable `` (via empty_cell.html). The matrix from `build_week_grid()` is already fully resolved -- this template only iterates, per PRD R2. Day headers ('Monday', ...) are abbreviated to 3 letters for column width, matching the precedent set by the landing page's decorative grid mock (Sprint 3); the full name is kept on the `title` attribute for accessibility (NFR-06). Wrapped in its own bounded, scrollable container (`overflow-x-auto`, per NFR-04 -- same idiom as the landing page's grid mock -- plus `overflow-y-auto max-h-[75vh]`) so the sticky header row / sticky time column (`sticky top-0` / `sticky left-0`) stick to *this* container's edges rather than the page's. Without a bounded height, this table's own `sticky top-0` header would fight the navbar's own `sticky top-0` (templates/partials/navbar.html) for the same on-screen position once the page scrolls past the fold -- not a documented PRD concern, but a necessary consequence of giving both a sticky header at the same time. Sprint 6 (htmx-interaction): `id="grid-table"` is the swap target every mutating block view (create/edit/delete/resize/repeat-across-days) declares via `hx-target="#grid-table" hx-swap="outerHTML"` (see apps/planner/views.py's module docstring for why every real mutation re-renders the whole table rather than a per-cell/per-column patch). `data-slot-interval` exposes `WeekGrid.slot_interval` (minutes) to `static/js/grid-drag.js`, which needs it to translate a dragged pixel delta into a whole number of slots -- read fresh from this element's own `dataset` on every drag gesture, never cached in JS across a swap (this whole `
