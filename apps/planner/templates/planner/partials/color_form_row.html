Same accepted edge case as `block_form.html`: only one "add color" attempt is ever open at once. - Edit mode retargets to `#color-row-{pk}` -- a specific color's own row id, since (unlike create) there is a concrete pk to key off here that cannot itself have changed underneath the request. - Cancel restores the prior fragment via a plain `hx-get` to `planner:palette` (create -- restores the "+ Add color" trigger) / `planner:color-cancel` (edit -- restores that color's display row), targeting `closest [data-color-row]` -- this root `
` itself carries `data-color-row` too, so `closest()` (which, per the DOM spec, always matches the starting element first before walking up) resolves to this very wrapper in both modes with the one selector, exactly mirroring `block_form.html`'s `closest td` precedent. - The `hex_code` field is hand-rendered below rather than run through `partials/form_field.html`, for the same class of reason `block_form.html` hand-rolls its color-swatch `RadioSelect`: a native `` companion picker isn't a Django form field at all, and both the picker and the text input need a shared `data-hex-sync` attribute for `static/js/color-sync.js` to pair them -- something the generic field-rendering partial has no hook for. {% endcomment %}
